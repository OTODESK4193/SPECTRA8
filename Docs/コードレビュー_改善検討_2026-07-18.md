## ■ Vocoderタブ

### 1. BPFBANKは高性能か？

実装 (FilterbankVocoder): ZDF-SVFのBPFを2段カスケード、melスケール48バンド固定配置 (80–7500Hz)、Q=10固定。

構造自体は正しく数値的にも安定だが、**2つの明確な弱点**がある。

**(a) Q=10固定がmel配置と合っていない**
melスケールでは低域のバンド間隔は狭く(ほぼ等Hz間隔)、高域は広い。Q=10固定だと:
- 低域: 帯域幅 8Hz@80Hz に対し隣接バンドまで約40Hz → **バンド間に大きな谷**(モジュレーターの情報が落ちる)
- 高域: 帯域幅 700Hz@7kHz に対し隣接間隔約300Hz → 過剰オーバーラップでボヤけ

改善案: Subtractive用に計算済みの `mBandEdges` から各バンドの帯域幅を導出し、**バンド毎に Q_i = f0_i / (edgeHi_i − edgeLo_i) × 定数** とする(定オーバーラップ設計)。一流ボコーダー(EMS/Sennheiser系)は全て帯域幅をバンド間隔に連動させている。効果が大きい割に変更は数行。

**(b) BAND数を減らすと高域が消える(バグに近い)**
`mBandF0` は48バンド分固定で `prepare()` 時のみ計算。`bandCount=8` にすると**下から8本だけ**が処理され、カバー範囲が 80〜数百Hz に縮む。8バンドボコーダーとして期待される「80–7500Hzを8分割」にならない。
改善案: bandCount変更検出時に mBandF0/mBandEdges を再計算して全域を再スパン(フィルタ状態リセット+短いフェードで切替クリック回避)。

**(c) CPU**: 合成側の係数 (`tan()`) を毎サンプル×全バンド計算している。formantShift/Stretchは制御ブロック(32smp)毎にしか変わらないので、**制御ブロック毎のキャッシュ**で大幅削減可。

### 2. ノブのスムージング

**パラメータ自体のスムージング(juce::SmoothedValue等)は未実装**。現状あるのは DSP 内部の平滑化のみ(LPCのG att/rel、kのブロックランプ、ポルタメント、入力エンベロープ)。

| パラメータ | 更新粒度 | リスク |
|---|---|---|
| mix / outputLevel | **ブロック毎1回** (〜10ms) | オートメーションでジッパーノイズ大 |
| detune / noise / lofi / wtPos / pulseWidth | 32smp (2ms) | 軽微な階段状変化 |
| formantShift / Stretch | 32smp、フィルタ係数が即ジャンプ | 高速変調でクリック感 |
| character / bandGains(EQ) | 32smp / 即時 | 軽微 |

改善案: `juce::SmoothedValue<float>` を最低限 **mix・outputLevel・detune・noise・formantShift** に導入 (10–20ms)。mix/outputLevel はアップサンプリングループ内で per-sample `getNextValue()` にするだけで効果大。
※ stereoWidth は現在 1.0f ハードコードで未接続(既知)。

### 3. Subtractive LR4 — 廃止 or 改善

音に魅力がない理由は構造的:
- 各バンドが**フラットトップ+急峻エッジ(48dB/oct)** → バンド中心の共振強調が無く、全バンド合算するとほぼフラットな応答 = 「ボコーダーらしい癖」が出ない。BPF Bank は Q=10 の共振が音色の個性そのもの。
- 音量差: `kSubMakeup=256(+48dB)` は一点の実測較正(マジックナンバー)で、素材・バンド数・EQ設定によりBPFとズレる。両タイプとも解析的に正規化してから共通トリムを掛けるのが本筋。

改善するなら(廃止前に試す価値がある順):
1. **エッジ共振化**: HPF/LPFセクションのQを0.707→1.2〜2.0に上げ、バンド端にピークを持たせる(いわゆるresonant edge。実装1定数)。
2. 合成側バンド中心に軽いピーキングEQ(+3〜6dB, Q≈2)を追加してBPFとのハイブリッド化。
3. それでも魅力がなければ廃止し、代わりに「BPFのQをノブ化(Bandwidth/Resonanceノブ)」した方がユーザー価値が高い。

なお合成側は毎サンプル `tan()`×2 + `computeBandNorm()` を全バンドで実行しており、BPFよりかなり重い。残す場合は制御ブロックキャッシュ必須。

### 4. LPCモードの窓の種類

**実装は正しい**(3種の窓テーブル、エネルギー正規化 `1/√Σw²`、ラグ窓)。違いが分かりにくいのは実装ミスではなく理論通り:

- 窓の差は主に**サイドローブレベル** (Hann −31dB / Hamming −42dB / Blackman −58dB) とメインローブ幅。
- LPCは自己相関からスペクトル包絡だけを推定するため細部の差が既に出にくい。
- さらに **σ=50Hzのガウスラグ窓**が自己相関を平滑化し、窓の差をほぼマスクしている。

つまり「差が小さいのが正常」。差を出したい/価値を上げたいなら:
- 窓切替と同時に**ラグ窓σも切替**(Hann=50Hz / Hamming=30Hz / Blackman=70Hz など)して実効的な包絡平滑度を変える
- あるいはパラメータを「窓の種類」から「**窓長切替**(128/256/384smp = 8/16/24ms)」に変更する方が音の差(時間分解能vs周波数分解能)は圧倒的に分かりやすい

**別件で見つけた重要な点**: 窓長256smp(16ms) < ホップ320smp(20ms@50Hz既定) のため、**フレーム間に4msの未分析区間**がある。低フレームレートではさらに拡大。窓長をホップ長以上(または320smp)にすると子音の取りこぼしが減る。

さらに: **プリエンファシスが無い**。古典LPC(TMS5220含む)は分析前に 1−0.94z⁻¹ の高域強調を入れ、合成後にデエンファシスで戻す。これが無いと高次フォルマントの推定が弱く、こもった音になりやすい。明瞭度改善の余地として最有力。

### 5. K量子化(低ビット)でクリップする

原因は2つ:
1. **kドメイン一様量子化**は |k|→1 付近で極半径への感度が極端に高い。3bit(Q=3)だと 0.83 が 1.0→クランプ0.995 に丸められ、共振が急増してエネルギーが跳ね上がる。
2. ゲインGは**量子化前**の予測誤差エネルギーEから計算されるため、量子化で共振が増えてもGが下がらず過大入力になる。

対策(推奨順):
- **(a) ゲイン補償**: 量子化後に `G *= sqrt(Π(1−kq²) / Π(1−k²))` を掛ける。フィルタの利得変化を打ち消す最も直接的なクリップ対策。実装は量子化ループに数行追加。
- **(b) LAR(またはarcsin)領域で量子化**: `q(atanh(k))` を丸めて `tanh` で戻す。|k|大での感度が均等化され、TMS5220系の実機も非一様テーブルを使う。BitSpeekらしさは保たれる。
- (c) 量子化後クランプを 0.995→0.97 程度へ(応急処置、音は少し丸くなる)。

(a)+(b) の併用が理想。レトロ感(粗さ)は残り、音量暴れだけが消える。

### 6. Lofiノブで低音が強調される件

原因は `applyLoFi()` のサンプル&ホールド:
- ホールドレートが最低 **100Hz** まで下がるため、キャリアの基本周波数より低くなると **S&H周期そのものが新しい低周波の周期(サブハーモニック)** として聞こえる = 低音強調の正体。
- 加えてZOHのsincロールオフで高域が減衰し、相対的にさらに低域寄りに。

希望の「元音の高さでLofiになる」は**ピッチ同期デシメーション**で実現できる:
```
holdPeriod = kInternalSampleRate / (N × activePitch)   // Nはピッチあたりのステップ数
```
lofi を上げると N を 64→4 のように減らす。ホールドレートが常に基音の整数倍なので**音程は保たれたまま**倍音だけが粗くなり、まさに「元音の高さでLofi」の味付けになる。activePitch は PluginProcessor から syncParameters 経由で渡せばよい。

その他:
- 最低レートを100Hz→2kHz程度に上げるだけでも即効性あり(簡易案)。
- `lofi > 0.5` で**隠しピッチ半音量子化**が発動する仕様は気付きにくい。ケロケロは pitchQuantize ノブに一本化し、この分岐は削除推奨。
- S&H前に簡単なLPFを入れるとエイリアスの荒れを制御できる(あえて残すのも味)。

### 7. NoiseMix −100% とは何か

実装 (PluginProcessor §NOISE±):
- **LPCモード**: 0%=ピッチ検出のV/UV(有声/無声)に自動追従(無声部だけノイズ励起)。+100%=常時全ノイズ(ウィスパー)。**−100%=ノイズ完全除去=無声子音も含め全てトーン励起**。子音の明瞭度が落ちち、純ロボット声になる(BitSpeekの Tone/Noise バランス相当)。
- **Filterbankモード**: 負値は0にクランプ = **−100〜0%は何も変わらない**。

改善案: モードで意味が変わるのはUI上分かりにくい。Filterbank選択時はノブ範囲を0〜100%に切替(またはツールチップ/負域グレーアウト)、LPC時は中央デテント付き −100/0/+100 表示が親切。

## ■ EXCITATIONタブ

### 8. Detuneの単位表記 (Cent + 度数)

現状 `setTextValueSuffix(" cents")` のみ。パラメータ定義に `withStringFromValueFunction` を足すのが正道(ホストのオートメーション欄にも反映される):

```cpp
layout.add(std::make_unique<juce::AudioParameterFloat>(
    juce::ParameterID("detune", 1), "Detune",
    juce::NormalisableRange<float>(0.0f, 1200.0f), 5.0f,
    juce::AudioParameterFloatAttributes().withStringFromValueFunction(
        [](float v, int) {
            static const char* names[] = { "1度","短2度","長2度","短3度","長3度",
                "完全4度","増4度","完全5度","短6度","長6度","短7度","長7度","8度" };
            const int st = (int)std::round(v / 100.0f);   // 半音数
            return juce::String((int)v) + " ct (" + names[juce::jlimit(0,12,st)] + ")";
        }));
```
表示例: `700 ct (完全5度)`。GUI側は suffix を外すだけ。

### 9. Detuneアルゴリズムは高度か？ → Dune3風の複数選択

現状は**シンプルなユニゾン**: ボイス番号で符号交互・固定倍率(0.15/0.25…)のL/R対称デチューンのみ。位相ドリフトや分布制御は無く、高度とは言えない。

「Detune Mode」(AudioParameterChoice) 追加案 — ExcitationEngine の `detuneOffset` 計算を分岐するだけで実装可能:

| モード | 内容 |
|---|---|
| Classic | 現行(互換維持) |
| Linear | ボイスを −1…+1 に等間隔配置 × detune量(スーパーソウ的) |
| Exponential | 中心に密・外側に疎の指数分布(Dune3のデフォルトに近い) |
| Random Drift | ボイス毎の低速ランダムウォーク(0.1–0.5Hz)で揺らす(アナログ感) |
| Chorus | ボイス毎に位相の異なる低速LFOで変調(コーラス的うねり) |

Random/Chorus はボイス構造体に位相/状態を1つ足すだけ。Auto(非MIDI)モードは3ボイス固定なので、Linear/Exp では3ボイスを −1/0/+1 に配置すると効果が分かりやすい。

### 10. カスタムWavetableブラウザ

実現可能。設計案:

**DSP側 (Wavetable.h)**
- `MorphWavetable` に `loadFromAudioData(const float* data, int numSamples)` を追加。2048サンプル/フレームで分割(Serum互換)、フレーム数可変。既存のFFT帯域制限ミップ生成ロジックをそのまま流用。
- RTセーフな差し替え: テーブル一式を `struct TableSet` にまとめ `std::shared_ptr<const TableSet>` を保持、ロード完了後に `std::atomic_store` でスワップ(オーディオスレッドはロックなしで読むだけ)。

**GUI側 (ExcitationPanel)**
- Waveform コンボで "Wavetable" 選択時のみ、コンボ右に Browse ボタンを表示。
- ボタン押下でノブ側エリア(2×2グリッド部)を `juce::FileBrowserComponent` に切替(カスタムフォルダを初期ディレクトリに設定、.wav フィルタ)。選択で読み込み→ノブ表示に戻る。
- 読み込みは `juce::AudioFormatManager` + `AudioFormatReader`(メッセージスレッド)。完了後 WaveDisplay を新テーブルの波形で更新。

**永続化**
- 選択パスを `apvts.state.setProperty("customWavetablePath", ...)` で保存し、`setStateInformation` で復元ロード。ファイル欠損時は内蔵テーブルへフォールバック+GUI通知。

**手順の目安**: ① Wavetable.h のロード+atomic swap → ② Processorにロード用ブリッジ(メッセージスレッドAPI) → ③ Panel の Browse ボタン+FileBrowser → ④ 永続化 → ⑤ WaveDisplay反映。

## ■ 追加検証 (2026-07-18)

### 11. Tracking 100%で「ポルタメント風」になる問題

**結論: Portaは無関係。ピッチ検出→適用パスの3つの要因の複合で、改善可能。**

現状のパス (PitchTracker + PluginProcessor):

1. **更新が16ms毎+32ms窓の平均値**: MPM分析はホップ256smp(16ms)毎。しかも512smp(32ms)窓全体の自己相関なので、得られるピッチは実際の抑揚を**時間平均した遅れた輪郭**。スピーチの速い抑揚がなまって「滑って追いかける」=ポルタメント感の主因。
2. **±20セントのデッドバンド**: `mLastVoicedPitch` 比で約20¢以内の変化は無視→超えた瞬間に一括ジャンプ。自然なイントネーションが「保持→跳び」の階段になり、うねり/グライド感を悪化させる。
3. **更新時に即値ジャンプ(ランプなし)**: 16ms毎にキャリア周波数が不連続に跳ぶ(Porta=0時はExcitationEngineのportaCoeff=1で即時反映)。跳びのチャープがグライドとして知覚される。
4. (副次) オクターブ補正の参照が遅い `smoothedHz` のため、有声開始直後に誤補正→スウープが混ざることがある。

**改善案(スピーチ/歌声のピッチ感を維持する設定)**:

| 対策 | 内容 | 効果 |
|---|---|---|
| (a) ホップ短縮 | kHopSize 256→**128 (8ms)** | 追従の時間分解能2倍。CPUは約2倍だが許容範囲(必要なら64=4msも可) |
| (b) デッドバンド廃止→対数域平滑 | 20¢デッドバンドを削除し、代わりに log2(Hz) 領域の1次平滑 τ≈5–8ms | 微小抑揚を潰さず、検出ジッタだけ吸収。「保持→跳び」の階段が消える |
| (c) サンプル毎ランプ | 更新値へ3–5msの線形ランプ(ExcitationEngineの既存portaパスを流用し、Tracking時のみ最小ランプ時間を強制) | 不連続チャープ除去。5ms程度ならポルタメントとしては知覚されない |
| (d) オクターブ補正の参照変更 | smoothedHz → mLastVoicedPitch 基準に | 有声開始直後のスウープ低減 |

(a)+(b)+(c) で「原音の抑揚をそのまま持つが、うねらない」トラッキングになる。これはケロ无しトークボックス系ボコーダーの標準構成であり、**スピーチ・歌声ともに原音のピッチ感維持は実現可能**。

補足: 完全に「原音と同じピッチ感」が欲しい用途では、ピッチ量子化(pitchQuantize)=0%・Tracking=100%・上記改善が前提。逆にケロケロ寄りにしたい時のために、(b)の平滑τをTrackingノブとは別の内部定数ではなく「Response (Fast/Natural/Smooth)」として出すのも一案。
